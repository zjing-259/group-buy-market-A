## 交易规则与实现

- 外部请求唯一键是 `(source, channel, out_trade_no)`。外部单号在明细表和请求锁表统一使用 `utf8mb4_0900_bin`（NO PAD），大小写、重音均按原值精确区分，唯一索引和查询采用相同规则。锁单及结算均回读核验原始单号。锁单与结算入口共用标识符校验，拒绝空白、首尾空格和超过数据库列长的值，外部单号仍为最多12字符。同渠道下更换用户、商品、活动、开团/参团参数或回调地址返回 `E0107`；不同渠道允许相同外部单号。
- 所有状态的已存在订单先做不可变参数核验，再返回原订单和金额快照；不重新试算，也不增加占位。开团请求的 `request_team_id` 固定为空字符串，参团请求保存原始团队号。
- 数据库事务按“外部请求锁 → 用户活动额度锁 → 配置共享锁 → 团队占位/明细写入”执行。额度锁不依赖 Redis 租约或进程内锁。唯一索引作为额外持久化防线；`biz_id` 使用固定长度摘要，但不承担外部请求幂等职责。
- 交易领域服务重新调用试算，忽略调用方传入的金额、活动名称、人数和时间等派生字段。请求活动必须与渠道商品映射一致，资格、限次、人数及价格使用同一组受共享锁保护的配置。锁单试算在事务所在连接同步查询，避免连接池被外层事务占满后等待异步查询。
- `isEnable` 必须为真才能下单，`isVisible` 不作为参与条件。人群位图缺失放行与哈希碰撞（BUG-018）仍属后续专项，本轮没有改变人群存储政策。
- 参团先执行团队 `SELECT ... FOR UPDATE`，取得行锁后再用新语句读取数据库时钟，复核活动有效期并执行占位条件 UPDATE，避免把等待前的 NOW 当成取得锁后的时间。UPDATE 核对活动、SKU、来源、渠道、回调地址、进行中状态、团队/活动有效期及余量；明细 INSERT SELECT 再检查有效期，若占位后已过期则整笔事务回滚。开团 INSERT 同样校验活动有效期。团队 SKU 不从价格推断。
- 原价、优惠额、实付额保存为个人订单快照，满足 `原价 = 优惠额 + 实付额`。原价和快照须能精确表示为两位小数；折扣计算结果按 HALF_UP 保留两位，最低实付 0.01，最大金额 999999.99。不允许零元购，非法负配置、实付高于原价、超列精度及非法表达式返回 `E0111`。N 策略仍表示“N 元购买”。合法直减/满减恰好抵扣全部原价时保留 0.01 最低实付。
- 锁单支付时间为 NULL；支付时间列为 `DATETIME(3)`，与 Java Date 的毫秒精度一致。API 的数值时间戳按 Unix 毫秒传输，字符串时间需保留毫秒及正确时区，不能先格式化为秒。结算按精确渠道业务键定位并核验用户、渠道与原始单号；SQL 绑定订单 ID、用户、来源和渠道，限定待支付状态。此限定并不表示 BUG-006/008 的全部幂等响应验收已完成。
- 回调地址在入口、团队、个人明细及通知任务表统一支持512字符；超过限制在锁单前拒绝，避免支付成团时才触发列长异常。
- 支付事实时间不得早于个人订单创建时间或开团时间，必须严格早于团队截止时间，且不得晚于本次校验时的服务器时间（不额外容忍未来时钟偏差）。截止前真实支付的迟到通知允许结算。仍保持“开团起点 + validTime 分钟”，没有擅自取活动结束时间的较小值。
- 开团起止时间由 MySQL 同一条 INSERT 中的 `NOW()` 生成，避免 Java 毫秒值写入秒级字段时进位，造成刚开团就无法参与。

新增错误码：`E0107` 请求冲突/旧请求无法核验，`E0108` 活动不一致，`E0109` 团队不可参与/归属不一致，`E0110` 无参与资格，`E0111` 非法金额，`E0112` 订单用户或渠道不一致。查无当前渠道订单仍返回 `E0104`。
