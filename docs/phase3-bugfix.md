## 通知协议与重试

- 只有 HTTP 200 且正文精确为 `success` 才确认送达。其他 HTTP 状态、非协议正文、空结果和网络异常均记录失败原因；响应资源在所有分支关闭。
- 锁单入口及实际发送入口都校验 HTTP/HTTPS 回调地址。空值、“暂无”、缺失主机、用户信息、片段和非法端口不能伪装通知成功。保留原512字符上限。
- 最多5次投递尝试，含首次；失败后的等待为60、120、240、480秒。达到上限进入状态3，可通过通知表的状态、次数、最后错误查见。
- `notify_count` 在成功认领时增加，代表已经获准开始的投递尝试。认领竞争失败不计次；认领后进程中断时无法确定是否已发送，保守计入本次尝试，避免未知结果无限重投。历史超限的待执行任务会转为可见终态。

## 并发与恢复

通知任务在独立数据库事务内原子认领，状态4表示处理中，持有唯一令牌和60秒租约；认领提交后才进行HTTP调用。每次HTTP调用最多10秒，连接3秒、读写各5秒，不自动重试或跟随重定向。

结果写回同时检查状态4、当前令牌和未过期租约。旧工作线程不能覆盖新结果或成功态。进程中断、结果更新失败时保留认领，租约到期后由扫描恢复；最后一次未知结果到期后转终态。按下次执行时间和ID扫描，每批最多50条，失败任务退避后为后续任务让出位置；单条异常不终止整个批次。

已提交结算仍返回成功，通知故障仅影响通知任务。接收端应按请求JSON中的 `teamId` 幂等处理：网络响应丢失、进程暂停超过租约等情况仍可能重投，本机制不承诺外部副作用恰好一次。
